# ТЗ: аккаунты и бэкенд

> Статус: черновик 2026-09-30, ждёт решений пользователя (раздел 12). Реализация — этапы 13–16.

## 1. Зачем
Сейчас весь прогресс живёт в одном браузере: localStorage (`tc-progress`, `tc-settings`) и IndexedDB (`tc-db`: сделки тренажёра, журнал). Если сменить телефон или очистить браузер, прогресс пропадёт. Спасает только ручной экспорт в файл.

Аккаунт даёт:
- **Синхронизацию.** Начал урок на компьютере, продолжил на телефоне: прогресс, XP, серия, журнал и сделки тренажёра одинаковы везде.
- **Облачную копию.** Прогресс не теряется при очистке браузера или смене устройства.
- **Основу для будущих функций:** турниры на одном графике, рейтинги, общий прогресс с друзьями (см. список идей — в рамках этого ТЗ они не делаются).

## 2. Принципы
1. **Local-first.** Приложение, как и сейчас, работает сначала с локальными данными. Сервер — это место синхронизации, а не условие работы. Офлайн (PWA) продолжает работать полностью.
2. **Гостевой режим остаётся.** Весь курс доступен без регистрации. Аккаунт добавляет синхронизацию и ничего не отнимает.
3. **Минимум личных данных:** e-mail, имя для приветствия и сертификата, хэш пароля. Никаких телефонов, документов и платёжных данных.
4. **Без биржевых ключей.** Бэкенд не подключается к Bybit от имени пользователя и не хранит API-ключи бирж. Курс по-прежнему не даёт инвестиционных рекомендаций.
5. **Секреты — только в переменных окружения хостинга.** В репозитории лежит `.env.example` без значений, `.env` в `.gitignore`. Правило CLAUDE.md про секреты уточняется (раздел 11).
6. **Бизнес-логика — чистые функции с тестами.** Слияние прогресса, валидация и правила синхронизации — в `packages/shared` или `src/lib/sync`. Их используют и клиент, и сервер.

### Стек бэкенда (рекомендация)
| Часть | Выбор | Почему |
|---|---|---|
| Рантайм | Node 24 LTS | Тот же, что и у фронтенда; один `npm` |
| HTTP | **Hono** | Лёгкий, строгие типы, работает на Node и на edge-хостингах |
| БД | **PostgreSQL** | Надёжно, бесплатные тарифы (Neon, Supabase-Postgres) |
| ORM и миграции | **Drizzle** | TypeScript-схема, SQL-миграции в репозитории |
| Валидация | **zod** | Общие схемы фронтенда и сервера в `@bulleak/shared` |
| Пароли | **argon2id** (`@node-rs/argon2`) | Рекомендация OWASP |
| Тесты | Vitest + **PGlite** (Postgres в WASM) | Настоящий Postgres в тестах без Docker; работает в CI |
| Письма | Resend (3000 писем/мес бесплатно) | Простой API; ключ — только в env |

Альтернатива «без своего сервера» — Supabase (Auth + Postgres + RLS). Кода меньше, но логика слияния и правила переезжают в SQL-политики, и появляется зависимость от чужой платформы. Рекомендую свой API: логика остаётся в TypeScript с тестами, как весь проект.

## 6. API (`/api/v1`, JSON)
**Auth**
- `POST /auth/register` `{email, password, name}` → 201 + сессия; письмо подтверждения
- `POST /auth/login` `{email, password}` → сессия
- `POST /auth/refresh` → новая пара токенов (ротация)
- `POST /auth/logout` → отзыв текущей сессии; `POST /auth/logout-all`
- `POST /auth/verify-email` `{token}`; `POST /auth/resend-verification`
- `POST /auth/forgot` `{email}` → всегда 200 (не раскрываем, есть ли такой e-mail)
- `POST /auth/reset` `{token, password}` → отзыв всех сессий

**Аккаунт**
- `GET /me`; `PATCH /me` `{name}`; `POST /me/password` `{current, next}`; `POST /me/email`
- `GET /me/export` → JSON как у текущего экспорта; `DELETE /me` `{password}`

**Синхронизация**
- `GET /sync/progress` → `{state, rev}`; `PUT /sync/progress` `{state, baseRev}` → 200 `{rev}` или 409 `{state, rev}`. При конфликте клиент сливает (раздел 7) и повторяет запрос
- `GET /sync/settings`, `PUT /sync/settings` — аналогично, правило «последняя запись побеждает»
- `GET /sync/records?kind=sim|journal&since=<rev>` → изменения после курсора (включая удаления) + новый курсор
- `POST /sync/records` `{kind, changes: [{uid, data|null, updatedAt}]}` → применённые `rev`

Все тела проверяются zod-схемами из `/shared`. Ошибки — `{error: {code, message}}` с русским `message` для UI.

## 7. Синхронизация и слияние
**Прогресс** — один документ, слияние чистой функцией `mergeProgress(a, b)` в `/shared` (с unit-тестами на каждое правило):
| Поле | Правило |
|---|---|
| `lessons[id]` | Объединение. `readAt` и `completedAt` — самые ранние, `quizBest` — максимум, `quizAttempts` и `timeSpentSec` — максимум |
| `exams[id]` | Объединение; `best` — максимум, `passedAt` — самый ранний |
| `achievements` | Объединение; время — самое раннее |
| `activity[day]` | Объединение по дням; по каждому полю — максимум |
| `xp` | Максимум из двух, но не меньше суммы XP по `activity` (офлайн-приросты с двух устройств не теряются) |
| `streak` | Пересчитывается из объединённой `activity` (`lib/gamification/streak`) |
| `quizAttempts` | Объединение по `(lessonId, at)`, сортировка, обрезка до 500 |
| `counters` | Максимум по каждому счётчику |
| `profile`, `tradingPlan`, `strategy` | Последняя запись побеждает (по `updatedAt`, поле добавляется миграцией v4) |

Слияние коммутативно и идемпотентно: `merge(a, b) = merge(b, a)` и `merge(a, a) = a`. Это проверяется property-тестами.

**Сделки тренажёра и журнал** — записи:
- Dexie v2: у каждой записи появляются `uid` (UUID, создаётся на клиенте), `updatedAt` и мягкое удаление `deleted`. Миграция проставляет `uid` существующим записям.
- Клиент хранит курсор `lastRev` для каждого типа. Изменения — в очереди `outbox` (таблица Dexie).
- Конфликт одной записи — побеждает больший `updatedAt`.

**Когда синхронизируемся:** после входа; через 3 с после изменения (debounce); при возврате на вкладку; раз в 60 с при активной вкладке; при появлении сети. Статус в карточке профиля: ✓ синхронизировано · ⟳ идёт · ⚠ офлайн/ошибка (подсказка с временем последней синхронизации).

## 8. Авторизация и сессии
- **Пароль:** минимум 8 символов, проверка по списку частых паролей (топ-10 000, локально). Хэш — argon2id (m=19 МБ, t=2, p=1).
- **Access-токен:** JWT (HS256, 15 мин), хранится только в памяти вкладки.
- **Refresh-токен:** случайные 256 бит, на сервере — только хэш, срок 30 дней, ротация при каждом `refresh`.
  - С собственным доменом (раздел 12, вариант А) — cookie `HttpOnly; Secure; SameSite=Lax` на API-поддомене; это лучший вариант.
  - Без домена (фронтенд на `github.io`, API на другом домене) — cookie стала бы сторонней и в Safari не работает. Тогда refresh-токен хранится в localStorage и защищается ротацией с детектом повторного использования, строгим CSP и коротким сроком. Это хуже; см. решения.
- **Защита от перебора:** rate limit — вход 5 попыток за 15 мин на e-mail+IP, регистрация 5/час на IP, `forgot` 3/час на e-mail. Ответы на неверный e-mail и неверный пароль одинаковые.
- CORS — только адрес фронтенда. Заголовки безопасности (HSTS, `X-Content-Type-Options`, CSP для API). Логи без паролей и токенов.

## 9. Фронтенд
- **Страницы:** `/login`, `/register`, `/forgot`, `/reset?token=` (hash-роутер: `#/reset?token=…`), `/verify?token=`.
- **Настройки → раздел «Аккаунт»:** имя, e-mail (подтверждён или нет), смена пароля, выход, выход на всех устройствах, скачать мои данные, удалить аккаунт.
- **Карточка профиля в сайдбаре:** для гостя — кнопка «Войти»; для вошедшего — имя из аккаунта и значок статуса синхронизации.
- **Модуль `src/lib/sync/`** (чистые функции: очередь, курсоры, слияние) и `src/features/account/` (UI). API-клиент — `src/api/` с автоматическим `refresh` при 401.
- **Адрес API** — `VITE_API_URL` при сборке. Если он не задан, сборка работает в чисто гостевом режиме: кнопок входа нет, всё как сейчас.

## 10. Качество
- **Unit:** `mergeProgress` (property-тесты), правила слияния записей, очередь `outbox`, миграция Dexie v2 и прогресса v4, zod-схемы.
- **Сервер:** тесты маршрутов на PGlite — регистрация, вход, ротация и повторное использование refresh-токена, rate limit, сброс пароля, конфликт 409, изоляция пользователей (чужие данные недоступны).
- **E2E:** регистрация → прогресс → вход в новом контексте браузера → прогресс на месте; офлайн → изменения → онлайн → синхронизация; два контекста с конфликтом → слияние. Сервер в e2e — локальный API + PGlite.
- **CI:** job фронтенда (как сейчас) + job сервера (typecheck, lint, тесты). Деплой API — только после зелёного CI.
- **Нагрузка:** одна синхронизация — не больше 2 запросов в штатном случае; `GET /sync/records` отдаёт не больше 500 записей за раз, с пагинацией.

## 11. Изменения правил проекта
- В CLAUDE.md правило «Никаких секретов и ключей API в репозитории. Приложение использует только публичные данные» заменяется на: «Секретов в репозитории нет. Ключи и пароли сервисов — только в переменных окружения хостинга; в репозитории `.env.example` без значений. Приложение не использует ключи бирж и не торгует от имени пользователя».
- Команды: `npm run dev:server`, `npm run db:migrate`, `npm run check` (+ сервер).
- Создание аккаунтов на хостинге, подключение домена и деплой API — внешние действия, их делает пользователь или Claude с явного подтверждения.
